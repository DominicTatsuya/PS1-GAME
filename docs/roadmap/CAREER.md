# CAREER.md — キャリア習得ロードマップ（PS1-GAME プロジェクト統合版）

このドキュメントは、SRE／プラットフォームエンジニアを目標とした習得計画を、個人開発中の Three.js 製ゲーム「PS1-GAME」を**学習の媒体**として束ねたものです。プロジェクト外部にあった先行版のスキルロードマップを、具体的なプロジェクトに紐づけて更新したものにあたります。

> **関連**: 本ドキュメントは「開発者本人が何を身につけるか」に集中しています。
> プロジェクトとして何を作るか（Phase 順タスク・実装方針）は `PROJECT.md` 側を参照してください。
> 本 CAREER.md の Phase 0〜2 は、`PROJECT.md` の Phase 4（AWS 公開）〜Phase 6（SRE）と対応しています（SAA-C03 取得は CAREER.md 側に閉じ、PROJECT.md には反映しません）。

---

## 目標像

事業会社の **SRE／プラットフォームエンジニア（構築・運用の IC 側）**。
報酬根拠が稼働時間でなく事業 KPI（可用性・コスト・開発速度）に紐づく＝人月モデルから外れた働き方。旗振り役ではなく、構築・運用の実務担当として成立させる。

## 学習の媒体：PS1-GAME

Three.js 製の PS1 風ブラウザゲームを **AWS 上に公開・運用する** 形で進める。これにより同時に手に入るもの：

- AWS / IaC / SRE の実地経験（座学でなく、動いている実サービスで）
- 公開 URL・IaC リポジトリ・監視ダッシュボードという、対外的に提示できるポートフォリオ成果物
- AI 支援開発（Claude Code）を統制しながら個人で本番運用した、という差別化ストーリー

## 現状スキルの位置づけ（要約）

- **転用可能な土台**：障害の原因切り分け、構成設計判断、ドキュメント化、ガバナンス判断、製造業ドメイン知識
- **逓減層（レガシー／AI 代替）**：Oracle 運用、Windows / ESXi、ASP.NET Core / C# / React 実装
- **希少な芽**：Claude Code 基盤の設計・運用 ← このプロジェクトがその実績になる
- **欠落（本ロードマップで埋める）**：クラウド（AWS）、IaC、可観測性 / SRE 実践

> この整理の git 実測による裏づけ（何が証跡化済みで何が未証跡か）は `../実績情報_取得マップ_確定版.md` を参照。

## Phase 0（〜3ヶ月）クラウドの設計語彙 ＋ 最小公開

- **AWS SAA（SAA-C03）取得**。Well-Architected の 4 観点（信頼性・性能・セキュリティ・コスト）は SRE の判断軸と重なる。（出典：AWS 公式試験ガイド）
- 並行ハンズオン：ゲームを最小構成で公開する。フロントを S3 + CloudFront、バックエンド（ランキング API）を Lambda + DynamoDB + API Gateway で**手動**構築（手順は `docs/infra/INFRA.md`）。
- **成果物**：動く公開 URL ＋ 構成図（Wiki / GitHub）。

## Phase 1（3〜6ヶ月）インフラのコード化（IaC）

- Phase 0 で手動構築した構成を **Terraform** で再現可能にする。
- ツール選定理由をリポジトリに明記する（推奨は Terraform：AWS 単一なら CDK / SAM も妥当だが、他クラウドや一般的な SRE 求人での転用度を優先。この判断の言語化自体が成果物）。
- **成果物**：`apply` で一から再構築できるリポジトリ ＋ README ＋ 選定理由ドキュメント。

## Phase 2（6〜12ヶ月）SRE 実践

> 本 Phase で埋める「欠落」領域の実測確認は `../実績情報_取得マップ_確定版.md` を参照。現職の実績は点型・線型・過程型の証跡があるが、クラウド可観測性の運用実績（定量型に近い）は無いことが確定している。

- CloudWatch でメトリクス / ログ / アラームを設定。
- ランキング API に **SLO**（可用性・レイテンシ）を定義。
- 障害を 1 件、**ポストモーテム**として記録（過去の ESXi / Oracle 障害の経験が分析の型として活きる）。
- コストレビュー（小規模でも「コストを見て最適化する」型を実践）。
- **成果物**：監視ダッシュボード ＋ SLO ドキュメント ＋ ポストモーテム 1 本。

## このプロジェクトで埋まらない部分（正直な明記）

- **コンテナ／Kubernetes**：静的 SPA ＋ サーバーレス構成では自然に出てこない。スキルとして欲しい場合のみ「Lambda の代わりに ECS / Fargate でバックエンドを動かす」別構成を任意の回り道として用意する。必須ではなく、優先度は公開・IaC・SRE の後。

## 注意点

- SAA は設計の証明であり、運用実務（IaC / 可観測性）は別に積む。資格 ＝ 実務ではない。
- レガシー診断力は捨てず、「クラウド上の障害切り分け」に接続して活かす。診断の思考は普遍、技術スタックは載せ替える。
- 旗振り役は目指さなくてよい。成果物が実績を語る。
- このプロジェクトは学習媒体なので、Claude Code に IaC を一括生成させず、自分で理解しながら段階的に進める（AI 過依存 ＝「誤りが見えにくくなる」リスクへの対処）。
- 移行の現実的な目安は 6〜12ヶ月。
