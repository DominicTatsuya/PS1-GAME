# SAA_ROADMAP.md — AWS SAA-C03 取得ロードマップ（PS1-GAME 学習媒体版）

このドキュメントは、`CAREER.md` の Phase 0（SAA-C03 取得）を、**実際に取得までやり切るための手順**に落としたものです。
`CAREER.md` が「何を身につけるか」、`PROJECT.md` が「何を作るか」を扱うのに対し、本ファイルは
**「体系的な毎日勉強が続かない前提で、どうやって SAA-C03 に受かるか」**という運用計画に閉じています。

> **関連**
> - 学習目標の全体像・目標像は `CAREER.md`。本ファイルはその Phase 0 の実行計画。
> - プロジェクト側のタスク（Phase 4〜6）は `PROJECT.md`。本ファイルのトラック A はそれを学習視点で束ね直したもの。
> - SAA-C03 取得の記録は `CAREER.md` 側に閉じ、`PROJECT.md` には反映しない（`CAREER.md` の方針を踏襲）。

---

## §0 設計思想（この計画が依拠する2つの前提）

このロードマップは、次の2つを**動かせない制約**として最初から織り込んでいる。
一般的な「毎日コツコツ」型の計画は、本人に完遂実績がないため採用しない。

1. **現プロジェクトの構成は SAA の出題範囲の一部しかカバーしない。**
   PS1-GAME は静的 SPA ＋ サーバーレス構成であり、試験の広い部分（VPC/EC2/RDS/ELB 系）が自然には出てこない。
   → だから「深い1本のポートフォリオ ＋ 使い捨てのラボ ＋ 最小化した座学残余」という**非対称構成**を採る。
   ポートフォリオを2本に増やして全範囲を無理に埋めようとすると、構成が学習都合で歪むため、それはしない。

2. **日々の勉強は続かない（本人の実績ベースの事実）。**
   このプロジェクト自体、半年以上放置されても復帰できた。それは `HANDOFF.md`・セッションログという
   「再開のための足場」を自分で用意していたから。
   → だから規律に頼らず、**「その回で閉じる成果物」＋「外部から与える締切」**で回す。
   毎日の意志力に依存する箇所を、意図的に2点だけに絞る（§5）。

## §2 出題ドメインと、現プロジェクトのカバレッジ

配点（採点対象のみ）:

| ドメイン | 配点 | PS1-GAME 構成での実地カバー |
|---|---|---|
| 1. Design Secure Architectures | **30%** | 部分。IAM 最小権限は深く触れる。**VPC/セキュリティグループ/NACL は触れない**。 |
| 2. Design Resilient Architectures | 26% | ほぼ無し。サーバーレスは可用性がマネージドで得られてしまい、**ELB/Auto Scaling/Multi-AZ を自分で組む経験が出てこない**。 |
| 3. Design High-Performing Architectures | 24% | 部分。CloudFront/S3/DynamoDB は触れる。**EC2 インスタンスタイプ・EBS・RDS/Aurora は触れない**。 |
| 4. Design Cost-Optimized Architectures | 20% | 部分。使う分の課金は見える。**EC2 購入モデル（Reserved/Spot/Savings Plans）は触れない**。 |

要点:
- **Domain 1 が最大配点（30%）で、C02 の 24% から増えた最頻出の落とし穴。** 構築で拾える IAM 以外（ネットワークセキュリティ側）に、意識的に座学時間を割く。
- **Domain 2 は現構成が最も弱い。** ここは使い捨てラボ（§4 B2）で能動的に拾わないと空白のまま残る。

## §3 トラック A：PS1-GAME を「運用まで」仕上げる（深さ・最初にやる）

**目的**: SRE 寄りのスキル（サーバーレス＋IaC＋可観測性）を、対外提示できる1本に深く積む。
各ユニットは必ず「その回で閉じる成果物」で終える。順序は依存関係どおり。

- [ ] **A0. ビルドを通す（前ゲート）**
  nvm で Node を 20/22 LTS に切替え、`npm run build` を通す。成果物: ローカルで `dist` が生成される。
- [ ] **A1. フロントを AWS 配信**（`PROJECT.md` Milestone 4.1）
  `dist` を S3 に置き、CloudFront 経由で HTTPS 公開。手順は `docs/infra/INFRA.md` §2。成果物: **動く公開 URL**。
- [ ] **A2. ランキング API を接続**（Milestone 4.3 ＋ 4.2 の接続）
  Lambda + API Gateway + DynamoDB をコンソール/CLI で手動構築し、既存のフロント送信コードを繋ぐ。手順は `docs/infra/INFRA.md` §3〜§5。成果物: **オンラインランキングが実際に動く**。
  - ここで IAM ロール/ポリシー（最小権限）を自分で書く ＝ Domain 1 の中核を実地で踏む。実体のポリシーは `docs/infra/INFRA.md` §4。
- [ ] **A3. IaC 化**（`PROJECT.md` Phase 5 / `infra/IAC_CHOICE.md` で Terraform 選定済み）
  A1・A2 の手動構成を Terraform で再現可能にする。一括生成でなく小さく `apply`→確認で刻む（`PROJECT.md` の作業方針）。成果物: **`apply` で一から再構築できるリポジトリ ＋ 選定理由ドキュメント**。
- [ ] **A4. 可観測性とポストモーテム**（`PROJECT.md` Phase 6）
  CloudWatch アラーム1本＋ダッシュボード、ランキング API に SLO（可用性・レイテンシ）を定義、意図的に1件壊してポストモーテムを書く。成果物: **監視ダッシュボード ＋ SLO ＋ ポストモーテム1本**。

> A で実地に埋まるのは概ね: S3 / CloudFront / IAM / Lambda / API Gateway / DynamoDB / CloudWatch。
> ＝ Domain 1 の IAM 側と Domain 3 の一部。**それ以外は A では埋まらない**（→ トラック B・C）。

## §4 トラック B：欠落範囲の使い捨てラボ（広さ・気が向いた時に差し込む）

**目的**: A で出てこない範囲を、手を動かして最低限の手触りを得る。**ポートフォリオにはしない。**

**ラボ共通ルール**（課金と放置リスクの管理）:
- **当日中に立てて壊す。** 翌日に持ち越さない。終わったら必ずリソース削除まで確認する。
- 成果物化しない。学んだ差分を数行だけメモに残す程度でよい。
- 社外ネットワーク（接続あり・課金あり）で行う（§5 の分割に従う）。

- [ ] **B1. VPC / ネットワークセキュリティ ラボ**（Domain 1 の残り半分）
  パブリック/プライベートサブネット、ルートテーブル、セキュリティグループ / NACL、SSM Session Manager 経由で入る EC2。「なぜ SSH ポートを開けずに入れるか」を説明できる状態にする。
- [ ] **B2. レジリエンス ラボ**（Domain 2・現構成の最大の空白）
  ALB → 複数 AZ の EC2（Auto Scaling Group）→ RDS Multi-AZ を組む。**インスタンスを1つ落として、復旧とフェイルオーバーの挙動を目で見る**。
- [ ] **B3.（任意）コンテナ回り道**（`CAREER.md`「任意の回り道」に対応）
  必要を感じた時のみ。B2 の構成の代わりに ECS/Fargate でバックエンドを動かす。優先度は B1・B2 の後。

## §5 トラック C：消去できない座学残余（最小化して最後に寄せる）

**目的**: 手を動かしても得られない部分（比較知識・料金・暗記）を片付け、受験する。

- [ ] **C1. 演習**: Ping-t 等で問題演習を回す（本人既定の資源）。間違えた設問のドメインを記録し、弱い側に寄せる。
- [ ] **C2. 暗記残余**: ラボで手に入らない比較・料金・トレードオフ。例）S3 ストレージクラスの使い分け、EC2 購入モデル（On-Demand/Reserved/Spot/Savings Plans）、RDS vs DynamoDB vs Aurora の選択基準。
- [ ] **C3. 受験日を予約する**: **A と B の大半が終わった時点で、先に日付を確定して外部締切を作る。** そのうえで C1・C2 を短期集中で詰める。

> **正直な注記**: C1 の問題演習だけは、構成をどう組み替えても「手を動かすこと」で代替できない残余として残る。
> 設計でできるのはこれを**小さく・遅くする**ことであって、ゼロにすることではない。§0 の前提2に対する、この計画の限界点。

## §6 進め方のルール（性分を直すのでなく、直さずに回す）

**方針**: 「毎日勉強できる自分」に変えることは目標にしない。**続けられる形式の方に作業を寄せる。**
根拠は本人の実績（半年放置しても復帰できた ＝ 足場さえあればバースト運用は機能する）。

依拠する作業様式:
- **バースト ＋ 再開足場 ＋ 成果物区切り。** 思い出した時にまとめて触る。各ユニットは `HANDOFF.md` 型の足場で再開可能に保つ。
- **接続要否での作業分割**（社内ネットワークで個人 AWS アカウントに繋ぐ懸念への対処）:
  - 業務時間の隙間（**接続不要**）: 試験ガイド読解、演習、構成図設計、コード記述、ドキュメント化。
  - 社外・自宅/テザリング（**接続あり・課金あり**）: A2 以降のコンソール/CLI 実構築、B の全ラボ。

**意志力を投入する箇所は、次の2点だけに絞る**:
1. **各ユニットを「その回で閉じる成果物」で終える**（公開 URL / 動く API / `apply` できるリポジトリ / 壊せる構成）。中途半端に開いたまま放置しない。
2. **C3 で受験日を予約し、外部締切を1つだけ持つ。**

日々の規律に頼る箇所を上記2点に限定し、それ以外は成果物と締切という外部の仕掛けに肩代わりさせる。

## §7 順序と依存（カレンダーではなくゲートで刻む）

日付では刻まない（守れない計画を立てても無駄なため）。ゲートの通過順だけを決める。

```
A0 → A1 → A2 ──→ A3 → A4        （深さ：見返りが早い順。まずここを進める）
              │
              └─ B1 / B2 を随時差し込み（広さ：変化が欲しくなった時に）
                        │
                        └─ 大半通過後に C3(受験予約) → C1/C2 短期集中 → 受験
```

- **A を先に置く理由**: 公開 URL という見返りが早く出て、手が動きやすいから。
- **B は差し込み**: A の単調さに飽きた時の気分転換として、広さを稼ぐ。
- **C は最後に時間を区切る**: 締切なしでは着手されないため、A・B の大半が終わってから予約で外圧をかける。
